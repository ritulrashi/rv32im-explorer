# Phase 4 Design Note: Workloads, Compiler Analysis, RESULTS.md

Status: **awaiting review**

Goal: run real kernels on the Phase 3 model, then explain *why* each variant
performs as it does, using the CPI stack, not just raw cycle counts. Every
number in `RESULTS.md` is generated by a script and carries provenance.
Anything not measured says so.

## 1. Workloads

All kernels use **int32** data. RV32IM has no floating point. Overflow wraps
mod 2^32, which is well defined in RISC-V and reproduced exactly by the
Python reference.

### 1.1 Hand-written assembly (`workloads/asm/`)

| Kernel | Variant | What changes |
|---|---|---|
| dot | `naive` | one multiply-accumulate (MAC) per iteration: `lw, lw, mul, add, addi, addi, bne` |
| dot | `unroll4` | 4 MACs per iteration into **4 independent accumulators**, combined at the end. Fewer branches, and the load→mul→add chains are interleaved, hiding load-use and MUL latency |
| gemm | `naive` | classic i-j-k triple loop: C[i][j] += A[i][k] · B[k][j], with B walked down a column |
| gemm | `tiled` | the same loop order, blocked into T×T tiles (T = 8) so that one tile each of A, B and C is reused while it is cache-resident |
| gemm | `unroll4` | naive with the k loop unrolled ×4 |
| gemm | `tiled_unroll4` | tiled, with the innermost loop unrolled ×4 |

**No "tiled dot product".** A dot product reads each element exactly once,
so there is no reuse for tiling to capture. Tiling it would only add loop
overhead. The spec's "naive, tiled, unrolled" is therefore met by GEMM (all
three, plus the combination) and by dot (naive and unrolled). I'd rather
explain why a tiled dot is meaningless than ship one.

### 1.2 C kernels compiled with clang (`workloads/c/`)

The same algorithms in C: `dot_naive.c`, `dot_unroll4.c`, `gemm_naive.c`,
`gemm_tiled.c`, `gemm_unroll4.c`.
- Compiled at **-O0 and -O3** with
  `clang --target=riscv32-unknown-elf -march=rv32im -mabi=ilp32 -ffreestanding -fno-builtin -nostdlib`.
- Linked with GNU ld from the RISC-V toolchain, using
  `workloads/common/link.ld` and `crt0.S` (sets up the stack, calls `main`,
  and writes `main`'s return value to `tohost`: 1 means pass).
- `-fno-builtin` stops clang from turning loops into `memset`/`memcpy` calls
  that we have no library for.
- There are no 64-bit types, so no `libgcc` helper calls are needed.

### 1.3 Problem sizes

| Kernel | Sizes | Footprint |
|---|---|---|
| dot | N = 1024 | 8 KiB (two vectors) |
| gemm | N = 32 | 12 KiB (three 32×32 matrices) |
| gemm | N = 64 | 48 KiB |

These sizes are deliberate:
- **`small_caches`** (1 KiB D-cache): everything exceeds it.
- **`big`** (16 KiB D-cache): dot and GEMM-32 fit, GEMM-64 does not.

So the same kernel moves from "fits" to "doesn't fit" across configs, which
is what makes tiling's effect visible.

### 1.4 Data, correctness, and the measured region

- **Data:** `workloads/gen_data.py --kernel K --n N --seed S` writes the
  input arrays (seeded values in 0..255) and the **expected result**,
  computed independently in Python, into an assembly data file.
- **Self-check:** after the kernel, the program compares a checksum of the
  result with the expected one and passes (`tohost = 1`) only on a match. A
  wrong kernel therefore can't produce a timing number. Every workload also
  runs in lockstep (ISS vs pipeline) as part of the suite.
- **Region of interest (ROI):** a store of 1 or 2 to a dedicated symbol
  `rvx_roi` marks the start and end of the measured region. The model
  snapshots every counter when that store **retires in WB**, and reports
  `roi = end − begin`. The ROI CPI stack still sums exactly to the ROI cycle
  count, because both snapshots do.
  - **Excluded:** setup, the checksum loop, and the pass/fail code.
  - **Included:** cold misses. Caches start cold, and setup touches no data
    arrays.
  - **Perturbation:** the marker store itself goes through the D-cache and
    allocates one line. It sits on its own line, so it evicts nothing of the
    kernel's. Documented in LIMITATIONS.
  - The ISS just sees ordinary stores, so lockstep is unaffected.

## 2. Configurations

Every workload runs under all five configs in `configs/`. The main tables
show three:
- **`baseline`:** ideal memory, static not-taken (the Phase 2 machine)
- **`small_caches`:** 1 KiB L1s, bimodal + BTB
- **`big`:** 16 KiB L1s, gshare + BTB

The other two (`bimodal_btb`, `gshare_btb`) appear in the full CSV. They
isolate the front end: same ideal memory, different predictor.

Everything runs on the **Release (-O3)** simulator build. Results are
deterministic, so each point is a single run, with no averaging and no error
bars. That is stated, not assumed: the script runs a sample of points twice
and checks the outputs are byte-identical.

## 3. What gets reported

**Per (workload, config):** ROI cycles; retired instructions; CPI; the six
CPI-stack components, in cycles and as a fraction of the ROI; D/I-cache miss
counts; conditional mispredicts; instructions per MAC.

**Compiler analysis (-O0 vs -O3):**
- the inner loop of each C kernel, extracted from `objdump -d` of the built
  ELF and shown in RESULTS.md (with the command that produced it)
- static instructions per inner iteration, and dynamic instructions per MAC
- loads and stores per MAC
- what clang changed relative to the naive source: register allocation,
  unrolling, strength reduction, loop interchange, if any

Any claim about what the compiler did must be backed by an assembly excerpt.

## 4. Hypotheses, written before measuring

Written down now so RESULTS.md can say honestly which held. Each one will be
marked confirmed, refuted, or partly true, with the evidence.

1. **dot naive on baseline:** dominated by load-use stalls (`lw` → `mul`) and
   MUL latency (+2 per MAC), plus a 2-cycle taken-branch penalty per
   iteration under static not-taken.
2. **dot unroll4** removes most of the branch cost (one branch per 4 MACs)
   and hides load-use/MUL latency by interleaving independent chains.
   Expect a large CPI drop on every config.
3. **GEMM tiled is *slower* than naive on `baseline`.** With ideal memory,
   tiling only adds loop overhead. This is the expected negative result, and
   I will measure rather than assume its size.
4. **GEMM tiled beats naive on `small_caches`** for both N, because naive's
   column walk of B misses on every access, and **on `big` only at N = 64**.
5. **Possible surprise:** arrays aligned to 4 KiB map A, B and C rows onto
   the same sets of a 2-way cache. That could cause conflict misses that
   tiling alone doesn't fix. If it shows up, I'll investigate with the miss
   counters and a padded-layout variant.
6. **clang -O0** keeps every variable on the stack, so expect several
   loads/stores per MAC and a high load-use share. **-O3** should be close to
   the hand-written naive loop. It may unroll on its own; that's checked in
   the assembly.

## 5. Code and script layout

```
workloads/common/rvx_workload.h   asm macros: ROI_BEGIN, ROI_END, PASS, FAIL, CHECKSUM
workloads/common/crt0.S, link.ld  C runtime: stack, call main, report to tohost
workloads/common/roi.h            C: roi_begin()/roi_end() as volatile stores
workloads/asm/*.S                 hand-written kernels
workloads/c/*.c                   C kernels
workloads/gen_data.py             seeded inputs + independent expected results
workloads/CMakeLists.txt          builds every (kernel, variant, size, opt) ELF
src/pipeline/                     ROI snapshots, plus an "roi" block in the stats JSON
scripts/phase4_run.sh             runs everything -> results/phase4/raw.csv + stats/*.json
scripts/phase4_tables.py          CSV -> results/phase4/tables.md (generated, never hand-edited)
RESULTS.md                        generated tables included verbatim, plus written analysis
```

**Tests added before measuring:**
- **ROI:** a hand-computed test, with the marker stores placed around a known
  hazard sequence.
- **Correctness:** every workload passes its self-check under every config,
  and runs in lockstep.
- **Data generator:** `gen_data.py` is checked against a tiny case computed
  by hand.

**Exit criterion:** RESULTS.md exists with tables for every kernel across at
least three configs, the -O0/-O3 analysis, the hypothesis outcomes, and at
least one negative or surprising result investigated.

## 6. Risks I'm flagging now

- **clang toolchain:** I haven't yet confirmed that the Codespace's clang 18
  has the riscv32 target and produces ELF objects that GNU ld links. I'll
  check this first. If it fails, I'll stop and tell you rather than quietly
  switching to GCC.
- **Simulation time:** GEMM-64 at -O0 is roughly 10M instructions per config.
  The model should handle that in seconds. I'll measure it and report it.
- **Kernels are not a benchmark suite.** They are small integer kernels on a
  scalar core. The conclusions are about this microarchitecture and these
  loops, and RESULTS.md will say so.
